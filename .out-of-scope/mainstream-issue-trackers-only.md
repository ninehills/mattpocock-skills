# 问题跟踪器集成仅限于主流工具

`setup-matt-pocock-skills` 仅为主流问题跟踪器提供一流支持。添加对小众、新型或单供应商实验性跟踪器的支持请求在范围外。

## 为什么在范围外

每个问题跟踪器后端都会将 CLI 形状硬编码到技能中（命令、标志、输出解析）。每个新后端都是永久的维护面——它必须随着工具的 CLI 演进而继续工作，并且必须继续针对 `/to-prd`、`/to-issues`、`/triage` 等进行测试。这个成本只对有意义比例的用户实际使用的跟踪器才值得。

"主流"是判断性标准，不是数字门槛：

- GitHub、GitLab 和 Backlog.md 是我们认为的主流工具——广为人知、广泛使用、远超实验阶段。
- 一个全新的、只有几百个 GitHub 星标的代理专注工具不是主流，无论其设计多么有趣。

星标、年龄和下载量在做决定时是有用的信号，但没有一个是规则。规则是：一个典型的工程师会认出这个工具并可能为他们的团队选择它吗？

非主流跟踪器的逃生出口已经存在：

- `local markdown` 用于轻量级的仓库内跟踪。
- `other/custom` 用于想要自己搭建的用户。

两者都不需要核心技能了解具体工具。
