# 范围之外的知识库

仓库中的 `.out-of-scope/` 目录存储被拒绝功能请求的持久记录。它有两个目的：

1. **机构记忆** — 功能被拒绝的原因，这样当 Issue 关闭时推理不会丢失
2. **去重** — 当新的 Issue 与先前的拒绝匹配时，技能可以提出来先前的决策而不是重新讨论

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，不是每个 Issue。多个请求同一内容的 Issue 归在一个文件下。

## 文件格式

文件应以轻松、可读的风格编写——更像简短的设计文档而非数据库条目。使用段落、代码示例和例子使推理清晰且对首次遇到它的人有用。

```markdown
# 暗黑模式

此项目不支持暗黑模式或面向用户的主题化。

## 为什么这超出范围

渲染管线假设在 `ThemeConfig` 中定义的单一调色板。支持多主题需要：

- 包裹整个组件树的主题上下文提供者
- 每个组件的主题感知样式解析
- 用户主题偏好的持久化层

这是一个重大的架构变更，与项目对内容创作的重点不一致。
主题化是下游消费者嵌入或重新分发输出时的关注点。

```ts
// 当前的 ThemeConfig 接口不是为运行时切换设计的：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，构建时解析
  fonts: FontStack;
}
```

## 先前请求

- #42 — "添加暗黑模式支持"
- #87 — "为无障碍性添加夜间主题"
- #134 — "暗黑主题选项"
```

### 命名文件

使用简短、描述性的 kebab-case 名称：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应该足以让浏览目录的人不打开文件就知道什么被拒绝了。

### 编写原因

原因应该是实质性的——不是"我们不想要这个"而是为什么。好的原因引用：

- 项目范围或哲学（"此项目专注于 X；主题化是下游关注"）
- 技术约束（"支持这个需要 Y，与我们的 Z 架构冲突"）
- 战略决策（"我们选择使用 A 而不是 B，因为……"）

原因应该是持久的。避免引用临时情况（"我们现在太忙了"）——那些不是真正的拒绝，是推迟。

## 何时检查 `.out-of-scope/`

在分诊期间（步骤 1：收集上下文），读取 `.out-of-scope/` 中的所有文件。在评估新 Issue 时：

- 检查请求是否与现有的范围外概念匹配
- 匹配是按概念相似性，而非关键词——"夜间主题"匹配 `dark-mode.md`
- 如果有匹配，向维护者提出来："这类似于 `.out-of-scope/dark-mode.md`——我们之前拒绝了它，因为 [原因]。你仍然有同样的看法吗？"

维护者可以：

- **确认** — 新 Issue 被添加到现有文件的"先前请求"列表中，然后关闭
- **重新考虑** — 范围外文件被删除或更新，Issue 按正常分诊流程进行
- **不同意** — Issue 相关但不同，按正常分诊流程进行

## 何时写入 `.out-of-scope/`

仅当**增强功能**（非 Bug）被拒绝为 `wontfix` 时。流程：

1. 维护者决定功能请求超出范围
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 如果存在：将新 Issue 追加到"先前请求"列表
4. 如果不存在：创建新文件，包含概念名称、决策、原因和第一个先前请求
5. 在 Issue 上发布评论解释决策并提及 `.out-of-scope/` 文件
6. 使用 `wontfix` 标签关闭 Issue

## 更新或移除范围外文件

如果维护者改变了对先前被拒绝概念的看法：

- 删除 `.out-of-scope/` 文件
- 技能不需要重新打开旧 Issue——它们是历史记录
- 触发重新考虑的新 Issue 按正常分诊流程进行
