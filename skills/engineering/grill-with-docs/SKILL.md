## 领域感知

在代码库探索期间，同时寻找现有文档：

### 文件结构

大多数仓库有一个单一上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，仓库有多个上下文。该映射指向每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

懒创建文件——只有当有内容要写时才创建。如果 `CONTEXT.md` 不存在，在第一个术语确定时创建。如果 `docs/adr/` 不存在，在第一个 ADR 被需要时创建。

## 会议期间

### 根据词汇表挑战

当用户使用与 `CONTEXT.md` 中现有语言冲突的术语时，立即指出。"你的词汇表将'取消'定义为 X，但你似乎指的是 Y——是哪一个？"

### 打磨模糊语言

当用户使用模糊或重载的术语时，提出精确的规范术语。"你说'账户'——你指的是客户还是用户？这是不同的东西。"

### 讨论具体场景

当讨论领域关系时，用具体场景来压力测试它们。设计探查边界情况的场景，迫使用户在概念之间的边界上保持精确。

### 与代码交叉引用

当用户陈述某事如何运作时，检查代码是否同意。如果你发现矛盾，提出来："你的代码取消整个订单，但你刚说可以部分取消——哪个是对的？"

### 内联更新 CONTEXT.md

当一个术语确定时，立即更新 `CONTEXT.md`。不要批量处理——在发生时捕获它们。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

不要将 `CONTEXT.md` 与实现细节耦合。只包含对领域专家有意义的术语。

### 谨慎提供 ADR

仅当以下三个条件同时满足时才提供创建 ADR：

1. **难以逆转** — 以后改变主意的成本很高
2. **没有上下文会令人惊讶** — 未来的读者会想"他们为什么这样做？"
3. **真实权衡的结果** — 有真实的替代方案，你因为特定原因选择了其中一个

如果三个条件中缺少任何一个，跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
