# ADR 格式

ADR 位于 `docs/adr/` 中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

懒创建 `docs/adr/` 目录——仅在第一个 ADR 被需要时创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：上下文是什么，我们决定了什么，以及为什么。}
```

就是这样。一个 ADR 可以是一个段落。价值在于记录*做了*什么决策以及*为什么*——而不是填写各个部分。

## 可选部分

仅当它们能带来真正价值时才包含这些。大多数 ADR 不需要它们。

- **Status** 前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——在决策被重新审视时有用
- **考虑的选项**——仅当被拒绝的替代方案值得记住时
- **后果**——仅当需要指出非显而易见的下游影响时

## 编号

扫描 `docs/adr/` 找到最高的现有编号并加一。

## 何时提供 ADR

以下三个条件必须同时满足：

1. **难以逆转** — 以后改变主意的成本很高
2. **没有上下文会令人惊讶** — 未来的读者会看代码并想"他们到底为什么这样做？"
3. **真实权衡的结果** — 有真实的替代方案，你因为特定原因选择了其中一个

如果一个决策容易逆转，跳过它——你只会逆转它。如果不令人惊讶，没人会想知道为什么。如果没有真实的替代方案，除了"我们做了显而易见的事"之外没什么可记录的。

### 什么符合条件

- **架构形态。** "我们使用的是 monorepo。" "写模型是事件溯源的，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带来锁定的技术选择。** 数据库、消息总线、认证提供者、部署目标。不是每个库——只是那些需要一个季度才能替换的。
- **边界和范围决策。** "客户数据由 Customer 上下文拥有；其他上下文只通过 ID 引用它。" 明确的"不"和"是"一样有价值。
- **刻意偏离显而易见的路径。** "我们使用手动 SQL 而不是 ORM，因为 X。" 任何合理读者会假设相反做法的事情。这些能阻止下一个工程师"修复"刻意为之的事情。
- **代码中不可见的约束。** "我们因为合规要求不能使用 AWS。" "响应时间必须在 200ms 以下，因为合作伙伴 API 合同。"
- **被拒绝的替代方案（拒绝原因不明显时）。** 如果你考虑了 GraphQL 但因微妙原因选择了 REST，记录它——否则六个月后有人会再次建议 GraphQL。
