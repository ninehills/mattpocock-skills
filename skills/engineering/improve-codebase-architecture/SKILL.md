# 改进代码库架构

揭示架构摩擦并提出**深化机会**——将浅层模块转化为深层模块的重构。目标是可测试性和 AI 可导航性。

## 词汇表

在每个建议中精确使用这些术语。一致的语言是关键——不要偏离到"组件"、"服务"、"API"或"边界"。完整定义见 [LANGUAGE.md](LANGUAGE.md)。

- **模块（Module）** — 任何有接口和实现的东西（函数、类、包、切片）。
- **接口（Interface）** — 调用者使用模块所需知道的一切：类型、不变量、错误模式、排序、配置。不仅仅是类型签名。
- **实现（Implementation）** — 内部的代码。
- **深度（Depth）** — 接口的杠杆：小接口背后大量行为。**深** = 高杠杆。**浅** = 接口几乎和实现一样复杂。
- **接缝（Seam）** — 接口所在的位置；可以在不就地编辑的情况下改变行为的地方。（使用这个，而不是"边界"。）
- **适配器（Adapter）** — 在接缝处满足接口的具体事物。
- **杠杆（Leverage）** — 调用者从深度中获得的好处。
- **局部性（Locality）** — 维护者从深度中获得的好处：变更、Bug、知识集中在一个地方。

关键原则（完整列表见 [LANGUAGE.md](LANGUAGE.md)）：

- **删除测试**：想象删除模块。如果复杂性消失了，它就是一个透传。如果复杂性在 N 个调用者中重新出现，它就发挥了作用。
- **接口就是测试表面。**
- **一个适配器 = 假设性接缝。两个适配器 = 真实接缝。**

此技能*受*项目领域模型的启发。领域语言为好的接缝命名；ADR 记录了技能不应重新讨论的决策。

## 流程

### 1. 探索

首先阅读项目的领域词汇表和你要改动区域的任何 ADR。

然后使用 Agent 工具，设置 `subagent_type=Explore` 来遍历代码库。不要遵循僵化的启发式——有机地探索并记录你感受到摩擦的地方：

- 理解一个概念需要在许多小模块之间跳转的地方？
- 模块**浅**的地方——接口几乎和实现一样复杂？
- 纯函数仅为了可测试性而被提取，但真正的 Bug 藏在它们如何被调用中的地方（没有**局部性**）？
- 紧耦合模块在接缝处泄漏的地方？
- 代码库中未测试的部分，或通过当前接口难以测试的部分？

对你怀疑是浅层的任何东西应用**删除测试**：删除它会集中复杂性，还是只是移动它？"是的，集中了"就是你要找的信号。

### 2. 展示候选

展示一个编号的深化机会列表。对于每个候选：

- **文件** — 涉及哪些文件/模块
- **问题** — 为什么当前架构导致摩擦
- **解决方案** — 用通俗英语描述会改变什么
- **好处** — 从局部性和杠杆角度解释，以及测试将如何改进

**使用 CONTEXT.md 的领域词汇，以及 [LANGUAGE.md](LANGUAGE.md) 的架构词汇。** 如果 `CONTEXT.md` 定义了"订单"，就说"订单接收模块"——而不是"FooBarHandler"，也不是"订单服务"。

**ADR 冲突**：如果候选与现有 ADR 矛盾，仅当摩擦足够严重值得重新审视 ADR 时才提出来。清楚标记（例如 _"与 ADR-0007 矛盾——但值得重新讨论，因为……"_）。不要列出 ADR 禁止的每一个理论重构。

不要提出接口。问用户："你想探索哪些？"

### 3. 审查循环

一旦用户选择了一个候选，进入审查对话。与他们一起走设计树——约束、依赖、深化后模块的形状、接缝后面是什么、哪些测试能保留。

当决策明确时，副作用内联发生：

- **深化的模块以 `CONTEXT.md` 中没有的概念命名？** 将术语添加到 `CONTEXT.md`——与 `/grill-with-docs` 相同的纪律（见 [CONTEXT-FORMAT.md](../grill-with-docs/CONTEXT-FORMAT.md)）。如果文件不存在，懒创建。
- **在对话中打磨了模糊的术语？** 立即更新 `CONTEXT.md`。
- **用户因关键原因拒绝了候选？** 提供 ADR，框架为：_"想让我把这记录为 ADR，这样未来的架构审查不会再次建议它吗？"_ 仅当原因确实是未来探索者需要避免再次建议相同事物时才提供——跳过临时原因（"现在不值得"）和不言自明的原因。见 [ADR-FORMAT.md](../grill-with-docs/ADR-FORMAT.md)。
- **想要探索深化模块的替代接口？** 见 [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md)。
