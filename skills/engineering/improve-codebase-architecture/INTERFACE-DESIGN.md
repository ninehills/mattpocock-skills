# 接口设计

当用户想要为选定的深化候选探索替代接口时，使用此并行子代理模式。基于"设计两次" (Ousterhout)——你的第一个想法不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 框定问题空间

在生成子代理之前，为选定候选编写面向用户的问题空间说明：

- 任何新接口需要满足的约束
- 它将依赖的依赖项，以及它们属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的说明性代码草图来落地约束——不是提案，只是使约束具体化的方式

将此展示给用户，然后立即进行步骤 2。用户在子代理并行工作时阅读和思考。

### 2. 生成子代理

使用 Agent 工具并行生成 3+ 个子代理。每个必须为深化的模块产生一个**截然不同的**接口。

用单独的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝后面是什么）提示每个子代理。简报独立于步骤 1 中面向用户的问题空间说明。给每个代理一个不同的设计约束：

- 代理 1："最小化接口——目标最多 1-3 个入口点。最大化每个入口点的杠杆。"
- 代理 2："最大化灵活性——支持多种用例和扩展。"
- 代理 3："针对最常见的调用者优化——使默认情况变得简单。"
- 代理 4（如适用）："围绕端口和适配器设计跨接缝依赖。"

在简报中包含 [LANGUAGE.md](LANGUAGE.md) 词汇和 CONTEXT.md 词汇，以便每个子代理的命名与架构语言和项目领域语言保持一致。

每个子代理输出：

1. 接口（类型、方法、参数——加上不变量、排序、错误模式）
2. 展示调用者如何使用的用法示例
3. 实现在接缝后面隐藏了什么
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——杠杆高的地方，薄弱的地方

### 3. 展示和比较

按顺序展示设计，以便用户可以吸收每个设计，然后用文字进行比较。从**深度**（接口的杠杆）、**局部性**（变更集中的地方）和**接缝放置**进行对比。

比较之后，给出你自己的推荐：你认为哪个设计最强以及为什么。如果不同设计的元素可以很好地结合，提出混合方案。要有主见——用户想要强有力建议，而不是菜单。
