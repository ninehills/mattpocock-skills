# 原型

原型是**回答问题的可丢弃代码**。问题决定了形状。

## 选择一个分支

识别正在回答的问题——来自用户的提示、周围的代码，或在用户可用时询问：

- **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个小型交互式终端应用，将状态机器推过纸上难以推理的用例。
- **"这个应该长什么样？"** → [UI.md](UI.md)。在单个路由上生成几种截然不同的 UI 方案，通过 URL 搜索参数和浮动底栏切换。

两个分支产生非常不同的产物——搞错这一点会浪费整个原型。如果问题真正模糊且用户不可达，默认选择哪个分支更匹配周围的代码（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明假设。

## 适用于两者的规则

1. **从第一天起就是可丢弃的，并清楚标记。** 将原型代码放在它实际将被使用的位置附近（在它为其原型化的模块或页面旁边），这样上下文是显而易见的——但命名要让随意的读者能看出这是原型，不是生产代码。对于可丢弃的 UI 路由，遵循项目已有的路由约定；不要发明新的顶级结构。
2. **一个命令运行。** 无论项目现有的任务运行器支持什么——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能够不假思索地启动它。
3. **默认不持久化。** 状态存在于内存中。持久化是原型*检验*的东西，不应该是它依赖的东西。如果问题明确涉及数据库，使用临时数据库或本地文件，带有清晰的"PROTOTYPE — 删除我"名称。
4. **跳过打磨。** 没有测试，没有超出使原型*可运行*之外的错误处理，没有抽象。重点是快速学习然后删除它。
5. **展示状态。** 在每个操作后（逻辑）或每次方案切换时（UI），打印或渲染完整的相关状态，以便用户可以看到什么改变了。
6. **完成后删除或吸收。** 当原型回答了它的问题后，要么删除它，要么将验证过的决策融入真正的代码——不要让它在仓库中腐烂。

## 完成时

*答案*是原型唯一值得保留的东西。在某个持久的地方（提交消息、ADR、Issue 或原型旁边的 `NOTES.md`）捕获它以及它正在回答的问题。如果用户在场，那次捕获是一次快速对话；如果不在，留一个占位符，以便他们（或你在下次访问时）可以在删除原型前填入结论。
