# 转为 Issue

使用垂直切片（曳光弹）将计划拆分为可独立领取的 Issue。

问题跟踪器和分诊标签词汇应该已经提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容开始工作。如果用户传递了 Issue 引用（Issue 编号、URL 或路径）作为参数，从问题跟踪器获取它并读取其完整内容和评论。

### 2. 探索代码库（可选）

如果你还没有探索代码库，去做以了解代码的当前状态。Issue 标题和描述应使用项目的领域词汇表词汇，并尊重你正在改动区域的 ADR。

### 3. 起草垂直切片

将计划拆分为**曳光弹** Issue。每个 Issue 是一个贯穿所有集成层端到端的薄垂直切片，而不是某一层的水平切片。

切片可以是"HITL"或"AFK"。HITL 切片需要人工交互，例如架构决策或设计审查。AFK 切片可以在没有人工交互的情况下实现和合并。尽可能优先选择 AFK 而非 HITL。

<vertical-slice-rules>
- 每个切片交付贯穿每一层（架构、API、UI、测试）的窄但完整的路径
- 完成的切片本身可演示或可验证
- 优先选择多个薄切片而非少数厚切片
</vertical-slice-rules>

### 4. 考查用户

将提议的拆分作为编号列表展示。对于每个切片，显示：

- **标题**：简短的描述性名称
- **类型**：HITL / AFK
- **被阻塞**：哪些其他切片（如有）必须先完成
- **涵盖的用户故事**：此切片涉及哪些用户故事（如果源材料有的话）

询问用户：

- 粒度感觉对吗？（太粗 / 太细）
- 依赖关系正确吗？
- 是否应合并或进一步拆分任何切片？
- 正确的切片是否标记为 HITL 和 AFK？

迭代直到用户批准拆分。

### 5. 将 Issue 发布到问题跟踪器

对于每个批准的切片，向问题跟踪器发布一个新 Issue。使用下面的 Issue 正文模板。这些 Issue 被认为是为 AFK 代理准备就绪的，因此除非另有指示，否则使用正确的分诊标签发布它们。

按依赖顺序发布 Issue（先发阻塞的），以便你可以在"被阻塞"字段中引用真实的 Issue 标识符。

<issue-template>
## 父级

对问题跟踪器上父 Issue 的引用（如果来源是现有 Issue，否则省略此部分）。

## 构建什么

此垂直切片的简明描述。描述端到端行为，而不是逐层实现。

避免特定的文件路径或代码片段——它们很快就会过时。例外：如果原型产生的片段比文字更精确地编码了决策（状态机、reducer、架构、类型形状），在此内联并简要说明它来自原型。裁剪到决策丰富的部分——不是可工作的演示，只是重要的部分。

## 验收标准

- [ ] 标准 1
- [ ] 标准 2
- [ ] 标准 3

## 被阻塞

- 对阻塞工单的引用（如有）

或"无 - 可以立即开始"如果没有阻塞。

</issue-template>

不要关闭或修改任何父 Issue。
