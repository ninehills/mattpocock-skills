# 审查

对 `HEAD` 与用户提供的固定点之间的 diff 进行双轴审查：

- **标准** — 代码是否符合此仓库文档化的编码规范？
- **规格** — 代码是否忠实实现了原始 issue / PRD / 规格？

两个轴作为**并行子代理**运行，这样它们不会相互污染上下文，然后此技能聚合它们的发现。

问题跟踪器应该已经被提供给你——如果 `docs/agents/issue-tracker.md` 缺失，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定固定点

无论用户说什么都是固定点——提交 SHA、分支名、标签、`main`、`HEAD~5` 等。不要有主见；直接传递。如果他们没有指定，问："基于什么审查——分支、提交还是 `main`？"在获得之前不要继续。

捕获 diff 命令一次：`git diff <fixed-point>...HEAD`（三点，以便与合并基进行比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

### 2. 识别规格来源

按以下顺序查找原始规格：

1. 提交消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 PRD/规格文件。
4. 如果什么都没找到，询问用户规格在哪里。如果他们说没有，**规格**子代理将跳过并报告"无可用规格"。

### 3. 识别标准来源

仓库中任何文档化代码编写方式的内容。常见位置：

- `CLAUDE.md`、`AGENTS.md`
- `CONTRIBUTING.md`
- `CONTEXT.md`、`CONTEXT-MAP.md`、每个上下文的 `CONTEXT.md` 文件
- `docs/adr/`（架构决策也是标准）
- `.editorconfig`、`eslint.config.*`、`biome.json`、`prettier.config.*`、`tsconfig.json`（机器强制的标准——记录它们但不重新检查工具已检查的内容）
- 仓库根目录或 `docs/` 下的任何 `STYLE.md`、`STANDARDS.md`、`STYLEGUIDE.md` 或类似文件

收集文件列表。**标准**子代理将读取它们。

### 4. 并行启动两个子代理

发送一条消息包含两个 `Agent` 工具调用。两个都使用 `general-purpose` 子代理。

**标准子代理提示** — 包含：

- 完整的 diff 命令和提交列表。
- 你在步骤 3 中找到的标准来源文件列表。
- 简要说明："读取标准文档。然后读取 diff。报告——按文件/块在相关处——diff 违反文档化标准的每个地方。引用标准（文件 + 规则）。区分硬性违规和判断性违规。跳过工具已强制执行的内容。不超过 400 字。"

**规格子代理提示** — 包含：

- diff 命令和提交列表。
- 规格的路径或获取的内容。
- 简要说明："读取规格。然后读取 diff。报告：(a) 规格要求但缺失或部分完成的需求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现看起来有问题的需求。为每个发现引用规格行。不超过 400 字。"

如果规格缺失，跳过规格子代理并在最终报告中注明。

### 5. 聚合

在 `## 标准` 和 `## 规格` 标题下展示两份报告，原文或轻微清理。**不要**合并或重新排序发现——两个轴是刻意分开的，以便用户可以独立查看。

以一行摘要结束：每个轴的总发现数，以及标记的最严重单一问题（如果有）。

## 为什么是两个轴

一个变更可以通过一个轴但失败另一个轴：

- 遵循每个标准但实现了错误的东西 → **标准通过，规格失败。**
- 完全按照 issue 要求做事但违反了项目约定 → **规格通过，标准失败。**

分开报告可以防止一个轴掩盖另一个轴。
